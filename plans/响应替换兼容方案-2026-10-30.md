# Qwen 上游响应替换兼容方案（2026-10-30）

## 范围与结论

本次仅交付方案、脱敏夹具和反例测试，不实现兼容、不改版本、不发版。核对基线为本仓库 `main` 的 `bcc177d`，项目版本 `0.3.20`。以下字段、状态、接口和版本均为提议，尚未与 chinzy 达成实现契约。

建议将逻辑响应与供应商响应分离：前缀 B 与继承其 item/content 的后继 C 归为一个逻辑响应 B；B 的供应商记录仅标记本地 `superseded`，逻辑响应由 C 的真实终态结束。全部原始供应商 ID、真实终态和用量保留。此模式只在显式协商 `response_supersede` 后启用。

## 提议的身份模型与状态机

逻辑响应是上层消费单位；供应商响应是原始证据单位。本次选择沿用首个 provider ID 作为逻辑 ID，避免 B Started 已公开后再改名：A→A，B→B，C→B，D→D。整个用户请求仍有三段逻辑响应，不强制把两次工具续答合并成一个超长响应。

建议维护如下会话内记录：

- 逻辑响应：稳定 logical ID、generation、当前 provider head、开始/结束发布标记、隔离状态、provider 成员及 item/content 别名。
- 供应商响应：原始 ID、原始 created/done event ID、最近真实 provider status、真实 terminal status（可空）、原始 usage（可空）、本地状态、superseded_by、父逻辑 ID。
- item：保留 provider scope 下的引入证据，同时以逻辑 item 关联媒体 facet 与工具 facet。B 的 message 不被 C 的 function_call 覆盖；二者共享 ID 但保留不同来源和类型。
- content：原始 owner 为 B/X/index，允许经一次已验证继承关系从 C/X/index 解析到同一逻辑 content；不伪造 C 的 content added 帧。

转换步骤：

1. 普通 created 维持既有流程。若已有符合条件的 B，仅把 C created 放入一个有界的候选槽，不公开第二个 Started、不提前弹出 `_followup_waiting`、不执行工具。
2. created 尚不含 item ID，不能在该帧断言替换。等 C 的首个 response-scoped item added 提供复用证据后，原子校验并提交 B→C：B.local_state=`superseded`，B.superseded_by=C，逻辑 B.head=C。B 不进入真实终态集合，也不标 completed/cancelled，不补 usage，不发送 provider cancel。
3. 候选上限建议为一个、2 秒、64 帧、256KiB（包含已知全局事件；仅候选相关数据入缓冲，累计计数仍有界），任一上限先到即 PROTOCOL_ERROR 并释放连接。候选之外仅允许既有合法 ASR/VAD/全局通知按原规则处理；第三个 created、候选首个 response 事件不是匹配的 item added、前缀在证明前发生终态/打断均不能套用替换规则。候选截止时间须与接收循环集成，即使没有后续帧也必须触发，不靠下一帧检查超时。
4. 按继承表解析 C 的媒体身份；原始 C provider 身份先验证，再将公开 OutputAudio/OutputText 的 response_id 映射为 B，item ID 和 index 保持一致。B 已公开的 AudioStarted 不再为 C 重复发布。
5. C function_call facet 单独登记；先用 C 原始身份核对 `_function_call_items` 及 arguments.done，再映射公开 ToolCallRequested.response_id 为 B。call_id 不映射、不重命名，结果回写与 ACK 仍以实际 call_id 绑定。
6. 收到 C 的真实 done 后，保留 C 的 status/usage，公开一次逻辑 B 的 ResponseFinished；其 local=false，状态/usage 来源为 C。它是逻辑终态，不是宣称供应商 B completed。诊断必须同时指明 terminal_source_provider_id=C。不把 B/C usage 合并成伪造的 provider usage。
7. C 完成后允许 D 正常建立；B 的本地墓碑不算 live 阻塞。`_current_response()` 应从未结束的逻辑响应选 head，绝不重新选中已 superseded 的 B；关闭也不能额外发布 B cancelled。

单个逻辑响应本期最多接纳 B/C 两个 provider 成员，不接纳递归替换或第三分支。证明候选期间的第三个 created、以及 C 尚未真实终态时的 D created，均失败；C 真实终态后的正常 D 不属于“第三条并发”。已有取消重叠例外与替换分开判定，不能借取消集合绕过替换上限。

### 迟到终态与重复事件

迟到 B.done 应按原始 B ID 验证，记录真实 status/usage/event ID，B.local_state 仍为 superseded。无论它在 C.done 前还是后到达，都不切换当前 head、不再公开 Started/Finished、不重复运行工具、不重放媒体、不把迟到 B usage 加到已经公开的逻辑终态。

供应商终态证据按 `(relay_session_id, provider_response_id)` 幂等记录，event ID 用于事件去重。相同终态重传只计一次；不同 event ID 携带冲突状态/usage 仍为 PROTOCOL_ERROR 并留下脱敏冲突诊断，不能统称“迟到事件”吞掉。迟到 B.done 在此前从未见过时是新真实证据，并非重复扣款授权。前缀的迟到媒体只作隔离计数，不输出；已 superseded 分支若又发新工具调用则失败。

## 必须保持的严格边界

| 情况 | 处理 |
| --- | --- |
| 未协商能力的重叠，包括该真实样本 | 原有 2026-08-28.3 行为不变 |
| 未知 response/item/content、空白/冲突 ID、跨 generation 或跨用户输入 item 的继承 | PROTOCOL_ERROR；先执行现有合法 user-side 旁路分类，不能扩大旁路范围 |
| C 未复用 B 唯一 live item、index 不同、content 已完成、B 已有音频/工具/终态、歧义多个 content | PROTOCOL_ERROR，不启发式猜归属 |
| B/C 两个独立完整输出或第三并发、递归替换、超出候选上限 | PROTOCOL_ERROR，不全局放宽并发数 |
| 同一 `(provider,item)` 重复 added、新 call_id 占用冲突、工具参数不合法 | 保留已有严格检查与参数错误处理，不因替换放行 |
| C 无 content added 但引用确切继承 content | 仅已提交继承关系内允许；其他 delta-before-content 仍失败 |

前缀字幕始终是 assistant 输出，不能注册成 user、不能回灌为用户输入。真实 input ASR final 的身份/去重仍由原 user identity 与 `_completed_inputs` 决定，保持一次 final；输出 transcript.done 不能被统计为输入 final。

工具幂等仍按原 external_session_id/call_id 状态，继承不重建 `_tools`/`_seen_tool_calls`。相同 event ID 的重传由接收循环去重；重复 call_id 的冲突及结果变更不能被静默接受。一次实际调用只允许一份结果与一次续答，所有 ACK 必须与输出及 call_id 匹配。

打断时隔离整个逻辑响应的 B/C 和未决候选，立即停止公开媒体和后续工具派发；不能将 superseded 视为用户取消。Qwen 现有 cancel 编码忽略显式 response ID，针对当前上游响应发送一次 cancel；不能向已实际完成的 head 再发送取消。生成中取消验收必须看到真实 cancelled/incomplete+取消原因，completed 不算。旧代际晚帧不能重新激活继承关系。

断线关闭仍遵循现有单终态所有权和资源释放。映射及候选清理，保留脱敏审计；重新绑定是新 generation、新上游会话，resume=false 不变。保持 ASR 去重、文字回灌、已确认用户身份及工具幂等的既有恢复边界。中继仍释放未结算预留，已结算部分不因断线退款。

## 显式协商提议

现有 authority 位于 `ARCHITECTURE/protocols/tokenseller-realtime-control-2026-08-28.3/` 及发布包中的同名目录。其 `manifest.json:21–31,58–77` 是消息及嵌套字段约束，并非可随意扩展的松散 JSON；所有控制对象严格拒绝未知字段。旧 open 只有 type/event_id/control_version/sdk_protocol_version/correlation/capability_digest，不存在 capabilities 字段。

`relay_control.py:132–194,201–226` 要求 capability 与打包 authority 一致；`98–99` 计算完整 capability 的摘要；`305–321` 构建 open；`323` 起校验 created 的精确字段、关联 event ID、版本、capability 及摘要。因此不能给旧 manifest 加一个字段后继续沿用旧版本。

建议单独建立新 authority（本次不创建）：

| 项目 | 建议取值/规则 |
| --- | --- |
| SDK 候选版本 | `0.3.21`，尚未修改或发布 |
| control_version | `2026-10-30.1` |
| sdk_protocol_version | `simple-harness-realtime/2` |
| wire_protocol / wire_version | `qwen-native` / `2026-10-30.1`，单独描述共享 item 及逻辑映射语义；原生事件类型/供应商 ID 不改写 |
| mint required_features | SDK 请求 `response_supersede`；中继选择支持的新 authority 和绑定凭据 |
| capability.features.response_supersede | 布尔值 `true` 表示中继支持本方案；参加完整 capability_digest 计算与 mint/open/created 绑定 |
| open.capabilities.response_supersede | 布尔值 `true` 表示 SDK 明确接受；新 open 必填 capabilities 对象，已知键必须为布尔值；false 禁用 |
| created.capabilities.response_supersede | 精确回显协商接受值；SDK 校验后才启用，不能仅凭本地版本号启用 |

启用条件为新三元版本匹配、mint 声明支持且 required_features 包含该能力、摘要/凭据绑定正确、open=true、created=true 全部成立。新增字段进入新 schema 的精确字段集合，不放松 `_exact_keys`。不支持 required feature 时明确 unsupported，在现有绑定校验阶段拒绝，不消耗凭据后再临时切换语义。

旧 SDK+旧中继、旧 SDK+新中继均保持旧协商及原串行语义，后者绝不向旧 SDK 偷发交错帧或新控制事件。新 SDK 未请求兼容时走旧 authority。新 SDK 请求 required 兼容但旧中继不支持时明确失败；仅调用方明确允许可选降级时，才重新以旧配置重新 mint/open，不复用已消费凭据，也不承诺降级能完成此复杂链。

新中继在 created 确认前继续阻止 provider 数据公开。确认后按真实供应商接收顺序转发这类重叠，不再等待 B.done；保留每个 provider 的 ID、音频、工具和真实终态。中继的并发预留/隔离上限独立存在，SDK 能力不是无限并发授权。

### 本地判定的传递

建议 SDK 增加只读 `response_identity_snapshot()`，返回不含正文的记录列表，字段至少为 provider_response_id、logical_response_id、generation、provider_status、provider_terminal_status、local_state、superseded_by、terminal_source_provider_id、item/content 绑定、真实 usage 或 null。`provider_status` 保留最后真实状态（B 为 in_progress），`provider_terminal_status` 在未见 done 时为 null，不把“尚未终态”写成 completed。

为向中继暴露 SDK 的确认，可在同一新 authority 中定义客户端控制帧 `tokenseller.response.superseded`：event_id、logical_response_id、prefix_provider_response_id、successor_provider_response_id、item_id、output_index、content_index、prefix_item_event_id、successor_item_event_id。帧隐式绑定当前 relay_session/generation，禁止跨连接复用；中继必须与该绑定下自己观察到的事件核对，按 prefix/successor 幂等记录。它只报告本地判断，不是终态或扣款指令，不携带字幕/音频/工具正文。仅对已协商 true 的新版本允许此事件；旧版本绝不发送。

终态仍由原始 provider done 提供；诊断事件将真实 C.done 与逻辑 B.finished 关联。诊断 schema 的安全字段白名单需同步扩展，不能把原始帧或正文塞进任意详情。此本地控制帧是否需要服务端 ACK、持久化失败是否影响释放，须在实施前与 chinzy 定稿；不依赖 SDK 帧送达才能执行断线释放。

## 账务对接待对齐项

SDK 提供证据和映射，不替 chinzy 决定结算政策，也不把逻辑 ResponseFinished 当新的计费对象。双方需在实施前明确：

1. B 仅有本地 superseded 时，中继如何标记审计并释放无真实终态的预留；释放触发点、持久化顺序、崩溃重试以及持久状态名称由中继确认。
2. C/D 以及 A 均按自己的真实终态/usage 对接结算，供应商 ID 不因映射合并；音频不能同时计入 B 和 C，SDK 逻辑 usage 与中继 provider usage 不能相加。
3. B 迟到终态如何记录真实用量，是否恢复原结算对象、由平台承担或采用其他政策，由 chinzy 决定。无论采用哪条，既有 provider 幂等键和账目冲正必须防止重复扣用户余额；SDK 不自动发送补扣命令。
4. 真实终态先到、结算或公开转发后到时，仍保持三个状态独立。SDK 接收/播放完成不等于账务完成，close 的 settlement=none 也不抹除先前已结算事实。
5. 中断及断线分别核对 B/C 的原始隔离状态、未结算预留释放、已结算保留、HELD=0 和守恒；superseded、用户取消、真实 completed 三者不得混为一个终态。
